# InsightFlow AI - Current Project Status

Last updated: 2026-10-06

## 1. Project overview

InsightFlow AI is a FastAPI and PostgreSQL data platform for uploading project-task CSV files, validating and cleaning the data, quarantining invalid records, generating analytics, and exposing the results through APIs and a dashboard.

The implemented high-level flow is:

```text
User authentication
    ↓
Workspace ownership
    ↓
Project ownership
    ↓
Project membership and roles
    ↓
Authenticated CSV upload
    ↓
Validation and cleaning
    ↓
Quarantine of invalid records
    ↓
PostgreSQL dataset storage
    ↓
Dataset-to-project ownership
    ↓
Profiling and analytics
    ↓
Role-controlled dataset and analytics access
```

## 3. Layer 1 - Ingestion and data engineering

### CSV upload

The backend provides:

```text
POST /upload
```

The endpoint:

- Accepts CSV files.
- Requires authentication.
- Requires a `project_id` form field.
- Confirms that the current user can upload to the project.
- Rejects missing filenames.
- Rejects non-CSV files.
- Rejects empty files.
- Rejects files larger than 5 MB.
- Reads the CSV with Pandas.
- Normalizes the dataframe before validation.

The upload request now contains:

```text
file         CSV file
project_id   Target project ID
Authorization Bearer token
```

### Data contract

The expected CSV columns are:

```text
Task_ID
Layer
Component
Status
Priority
Estimated_Hours
```

The required business fields are:

```text
Task_ID
Status
```

The validation layer checks:

- Missing expected columns.
- Unexpected columns.
- Missing values.
- Missing required fields.
- Exact duplicate rows.
- Duplicate `Task_ID` values.

### Cleaning and quarantine

The pipeline applies conservative cleaning rules:

- Trims column names.
- Trims string values.
- Treats empty strings as missing.
- Removes exact duplicate rows.
- Fills missing `Layer`, `Component`, and `Priority` values with `Unknown` when appropriate.
- Fills missing `Estimated_Hours` values with the available median.
- Does not invent missing `Task_ID` or `Status` values.
- Sends rows with missing required fields to quarantine.
- Sends rows with duplicate task IDs to quarantine.

Each upload produces:

```text
data/processed/{run_id}_ready.csv
data/quarantine/{run_id}_quarantine.csv
```

The UUID `run_id` connects the processed file, quarantine file, API response, and database pipeline record.

### Database persistence

For each upload, the system stores:

- Pipeline run metadata.
- Dataset metadata.
- Dataset version metadata.
- Dataset profile data.
- The cleaned dataset in a dynamically named PostgreSQL table.

The persisted `Dataset` now includes the target `project_id`, so a direct upload is immediately associated with its project.

## 5. Authentication and RBAC foundation

Authentication is implemented in `app/auth.py`.

Supported behavior includes:

- User registration.
- Password hashing with PBKDF2-SHA256.
- Password verification.
- Signed access-token creation.
- Token signature validation.
- Token expiration validation.
- Current-user lookup.
- Role-based route dependency support.
- FastAPI Bearer authentication for Swagger.

Authentication endpoints:

```text
POST /auth/register
POST /auth/login
GET  /auth/me
GET  /admin/users
```

Swagger authorization workflow:

1. Call `POST /auth/login`.
2. Copy only the raw `access_token`.
3. Click Swagger's `Authorize` button.
4. Paste only the token.
5. Do not add `Bearer`; Swagger adds it automatically.

## 6. Layer 3 - Workspace and project ownership

### Ownership chain

The current tenant ownership chain is:

```text
User
  ↓ owner_id
Workspace
  ↓ workspace_id
Project
  ↓ project_id
Dataset
```

### Workspace management

Workspace endpoints:

```text
POST   /api/workspaces
GET    /api/workspaces
GET    /api/workspaces/{workspace_id}
DELETE /api/workspaces/{workspace_id}
```

Workspace behavior:

- Workspaces belong to users.
- Users can list their own workspaces.
- Users can retrieve their own workspaces.
- Users can delete their own workspaces.
- Workspace ownership is checked on every protected operation.

### Project management

Project endpoints:

```text
POST   /api/projects
GET    /api/projects
GET    /api/projects/{project_id}
DELETE /api/projects/{project_id}
```

Project behavior:

- Projects belong to workspaces.
- A user can create projects only inside a workspace they own.
- A user can list and retrieve only projects in owned workspaces.
- A user cannot create a project in another user's workspace.
- Project deletion is ownership-protected.

## 7. Dataset ownership

Dataset ownership endpoints:

```text
PATCH /api/datasets/{dataset_id}/project
GET   /api/datasets
GET   /api/datasets/{dataset_id}
```

Dataset behavior:

- A dataset can be linked to a project.
- `project_id` is nullable for compatibility with older dataset rows.
- Dataset assignment checks project ownership.
- Dataset listing is now permission-aware.
- Dataset retrieval is now permission-aware.
- Members with view access can retrieve datasets in their projects.
- Unrelated users receive `404 Dataset not found`.

The older workflow was:

```text
Upload CSV
    ↓
PATCH dataset to project
```

The current preferred workflow is:

```text
Upload CSV with project_id
    ↓
Dataset is persisted directly under that project
```

## 8. Project-member permissions

The project-member permission system is implemented in:

```text
app/permissions/models through app/database/models.py
app/permissions/schemas.py
app/permissions/services.py
app/permissions/routes.py
```

### ProjectMember model

The `project_members` table connects users and projects.

Stored fields:

```text
id
project_id
user_id
role
created_at
```

The database enforces one membership per project-user pair with a unique constraint.

### Supported project roles

```text
viewer
analyst
editor
owner
```

### Permission endpoints

```text
POST   /api/permissions/projects/{project_id}/members
GET    /api/permissions/projects/{project_id}/members
PATCH  /api/permissions/projects/{project_id}/members/{user_id}
DELETE /api/permissions/projects/{project_id}/members/{user_id}
```

These endpoints allow the project owner to:

- Add a member.
- List members.
- Change a member role.
- Remove a member.

The API rejects:

- Unknown users.
- Duplicate memberships.
- Invalid role names.
- Member-management attempts by non-owners.

### Effective role resolution

The permission service resolves access in this order:

```text
Workspace owner → owner
Project member  → assigned member role
Other user      → no project access
```

Reusable checks include:

```text
user_can_view_project
user_can_edit_project
user_can_manage_project
```

## 14. Database and migration notes

The project currently uses:

```python
Base.metadata.create_all(bind=engine)
```

There is no Alembic migration system yet.

Important consequence:

- New tables can be created automatically.
- New columns are not reliably added to existing tables by `create_all`.
- The `datasets.project_id` column had to be added manually to the existing PostgreSQL database.

For production-quality development, the next database improvement should be adding Alembic migrations for:

```text
datasets.project_id
project_members
future permission changes
```

## 15. Known technical debt and follow-up work

### Legacy unprotected routes

The following older routes still exist separately from the ownership-aware APIs:

```text
GET /datasets
GET /datasets/{dataset_id}/preview
GET /pipeline-runs
GET /profiles/{dataset_id}
```

The analytics routes are now protected, but the legacy dataset and pipeline routes should be reviewed and either:

- Protected with authentication and project permissions.
- Moved under the ownership-aware API structure.
- Marked as internal-only.

### Upload implementation cleanup

The upload function contains an earlier temporary `Dataset` object before the database transaction. The actual persisted object is created inside the transaction. The temporary object should eventually be removed to reduce confusion.

### Session and architecture cleanup

Potential cleanup areas include:

- Consolidating repeated router imports.
- Standardizing database dependency functions.
- Moving upload workflow logic out of `main.py` into a dedicated service.
- Replacing broad exception handling around pipeline stages with structured error handling and logging.
- Adding explicit response models for more legacy endpoints.

### Authentication hardening

Future production hardening should include:

- Moving the application secret to a required environment variable.
- Rotating secrets safely.
- Adding refresh tokens or short-lived access tokens.
- Adding password reset and account management flows.
- Avoiding exposure of access tokens in screenshots or logs.

### Permission model improvements

Future permission features could include:

- Workspace-level members.
- Invitations and invitation expiration.
- Permission audit logs.
- Role-change history.
- Preventing owners from removing the final project owner.
- Explicit editor permissions for dataset reassignment and deletion.
- Separate analytics execution permissions from analytics viewing permissions.
